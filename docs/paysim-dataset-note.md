# PaySim Dataset Note

## Dataset

- Source: https://www.kaggle.com/datasets/ealaxi/paysim1?resource=download
- Kaggle title: `Synthetic Financial Datasets For Fraud Detection`
- Author on Kaggle: Edgar Lopez-Rojas
- License on Kaggle: `CC BY-SA 4.0`

## What This Dataset Is

PaySim is a public fraud dataset for mobile money transactions.

Important nuance: it is not a raw real-world transaction dump. It is a synthetic dataset generated by the PaySim simulator using aggregated patterns from a real mobile money service. That still makes it much better than the repo's current self-created training CSV for fraud modeling, but we should document it accurately.

For SentinelPay, the right description is:

- public dataset
- real-world-inspired
- simulator-generated
- suitable for fraud detection benchmarking and model training

## Data Context

From the Kaggle data card:

- the simulator is based on one month of financial logs from a mobile money service in an African country
- the Kaggle release is a scaled-down synthetic version of the original simulation
- `step` represents one hour
- total time horizon is `744` steps, or `30` days
- transaction types include `CASH-IN`, `CASH-OUT`, `DEBIT`, `PAYMENT`, and `TRANSFER`
- fraud is labeled in `isFraud`
- large illegal transfer attempts are labeled in `isFlaggedFraud`

Commonly cited dataset shape:

- about `6.36M` rows
- `11` main columns
- highly imbalanced fraud target

Main columns:

- `step`
- `type`
- `amount`
- `nameOrig`
- `oldbalanceOrg`
- `newbalanceOrig`
- `nameDest`
- `oldbalanceDest`
- `newbalanceDest`
- `isFraud`
- `isFlaggedFraud`

## Modeling Caveat

The Kaggle note explicitly warns that these balance columns should not be used directly for fraud detection because fraudulent transactions are cancelled in the simulation:

- `oldbalanceOrg`
- `newbalanceOrig`
- `oldbalanceDest`
- `newbalanceDest`

In practice, SentinelPay should treat those columns carefully:

1. do not blindly train on leakage-heavy fields
2. prefer derived behavioral and transactional features
3. validate any lift against temporal splits and ablation checks

## Why We Should Use It

The current repo ML path still uses self-generated synthetic training data for a baseline logistic regression model. PaySim is a stronger public benchmark because it gives us:

- a much larger sample size
- realistic transaction-type skew
- real fraud-class imbalance
- better benchmark credibility
- a clearer path for comparing simple ML against deeper models

## Recommended SentinelPay Positioning

We should describe the next ML phase as:

"Move the fraud scoring service from repo-generated demo data to the public PaySim fraud dataset, then optimize the model stack to catch as much fraud as possible while keeping false positives operationally manageable."

## Recommended Objective

For SentinelPay, the primary ML objective should be high fraud capture, not plain accuracy.

Preferred offline metrics:

- recall on `isFraud`
- PR-AUC
- precision at operational cutoffs
- false positive rate by transaction type
- calibration of the fraud score

Accuracy should not be a headline metric because the dataset is highly imbalanced.

## Recommended Model Progression

Start simple, then expand:

1. logistic regression baseline on curated features
2. gradient boosting baseline (`XGBoost`, `LightGBM`, or `CatBoost`)
3. sequence-aware or temporal deep learning only if it beats the tree baseline materially

Deep learning is allowed, but it should earn its place by beating strong tabular baselines on recall, PR-AUC, and operational stability.

## Planned Repo Direction

The repo should move toward:

- using PaySim as the default public training benchmark
- keeping the current self-generated dataset only for local smoke/dev convenience
- adding dataset ingestion, cleaning, and feature-prep scripts
- separating benchmark training from production inference packaging
- versioning model metadata with dataset source, feature schema, and evaluation scores

## Data Model Refactor Plan

### Core Decision

Do not reshape the live SentinelPay service contracts to match the raw PaySim CSV one-to-one.

Instead, split the ML data model into three layers:

1. raw dataset schema
2. canonical training schema
3. online inference feature schema

That keeps the product API stable while still letting the ML pipeline learn from PaySim.

### Layer 1: Raw PaySim Schema

Add an explicit raw-ingest model for the Kaggle CSV:

| Field | Keep | Notes |
| --- | --- | --- |
| `step` | yes | raw time unit from dataset |
| `type` | yes | map transaction type carefully |
| `amount` | yes | direct numeric input |
| `nameOrig` | yes | raw origin account identifier |
| `oldbalanceOrg` | yes, but caution | store raw value; do not trust as default model input |
| `newbalanceOrig` | yes, but caution | store raw value; possible leakage |
| `nameDest` | yes | raw destination identifier |
| `oldbalanceDest` | yes, but caution | merchant rows can be missing/zero |
| `newbalanceDest` | yes, but caution | merchant rows can be missing/zero |
| `isFraud` | yes | target label |
| `isFlaggedFraud` | yes | auxiliary rule-like signal |

Recommended raw struct:

- `PaySimTransactionRow`

This should live in the training pipeline, not in the production event contracts.

### Layer 2: Canonical Training Schema

Transform raw PaySim rows into a stable training schema that SentinelPay owns.

Recommended canonical training fields:

| Field | Source | Reason |
| --- | --- | --- |
| `time_step_hour` | `step` | temporal ordering |
| `transaction_type` | `type` | core behavioral signal |
| `amount` | `amount` | core numeric signal |
| `origin_id` | `nameOrig` | sequence/group features |
| `destination_id` | `nameDest` | sequence/group features |
| `origin_is_merchant` | derived from ID prefix | entity type signal |
| `destination_is_merchant` | derived from ID prefix | entity type signal |
| `is_flagged_fraud` | `isFlaggedFraud` | benchmark auxiliary signal |
| `label_is_fraud` | `isFraud` | supervised target |

Recommended derived canonical fields:

| Field | Derived from |
| --- | --- |
| `hour_of_day` | `step % 24` |
| `day_index` | `step / 24` |
| `is_cash_in` | `type` |
| `is_cash_out` | `type` |
| `is_debit` | `type` |
| `is_payment` | `type` |
| `is_transfer` | `type` |
| `log_amount` | `amount` |
| `origin_balance_delta` | balances, if retained for experiment only |
| `dest_balance_delta` | balances, if retained for experiment only |
| `origin_has_zero_balance_info` | balance columns |
| `dest_has_zero_balance_info` | balance columns |

### Layer 3: Online Inference Feature Schema

Do not replace the current `transactions.enriched` contract with PaySim columns.

The ML service should keep consuming the current enriched online event, but we should align its feature names with the canonical training schema where possible.

Current online schema already has many strong production-oriented derived fields:

- `amount`
- `amount_usd_equivalent`
- `amount_risk_tier`
- `senderTxCount24h`
- `senderTotalAmountUsd24h`
- `receiverInboundCount24h`
- `is_first_time_receiver`
- `is_new_device`
- `is_overseas`
- `is_cross_border`
- `tx_count_1m`
- `tx_count_1h`
- `tx_amount_1hour`

This is better than forcing raw PaySim fields directly into runtime inference.

### What We Should Add

Add to the ML training pipeline:

- raw PaySim row model
- canonical training row model
- explicit feature manifest
- dataset metadata manifest
- leakage-check report

Potential runtime additions worth considering later:

- normalized transaction subtype aligned with PaySim categories
- explicit `hour_of_day` or `event_hour`
- explicit `day_index`
- explicit sender/destination entity-type flags

### What We Should Not Add Blindly

Do not immediately push these raw fields into the production event contracts:

- `oldbalanceOrg`
- `newbalanceOrig`
- `oldbalanceDest`
- `newbalanceDest`
- `nameOrig`
- `nameDest`
- `isFraud`
- `isFlaggedFraud`

Reasons:

1. some are label/training-only
2. some risk leakage
3. some are simulator-specific raw identifiers
4. some do not belong in online inference contracts

### What We May Remove From ML Training Inputs

The repo's current local synthetic ML inputs include fields that do not map cleanly to raw PaySim without a derivation step, for example:

- `is_night`
- some wallet-specific synthetic heuristics

Those should either:

1. be re-derived from canonical time features, or
2. be dropped from the benchmark training set

### Recommended Mapping Strategy

Use this rule:

- raw dataset fields stay in offline ingestion
- derived canonical fields become benchmark training inputs
- production online events remain product-oriented and are mapped into the same feature space by a feature builder

That lets the same model family be trained offline on PaySim and served online on `transactions.enriched`.
